# Codex Autopilot v1.0 — целевая спецификация

Источник правды для всех задач прогона v1.0. Каждый воркер читает
относящийся к его задаче раздел целиком, а не пересказ в промпте.

---

CURRENT BASELINE
==================================================

v0.9 уже реализован и содержит:

- DAG задач, контракты и аддитивную миграцию;
- детерминированный dependency scheduler;

- параллельные App Server workers;

==================================================
ЧТО ФАКТИЧЕСКИ СЛОМАНО В v0.9 — ПРОВЕРЬ ПЕРВЫМ ДЕЛОМ
==================================================

Три дефекта установлены измерением, не предположением. Начни с них,
потому что без них любая новая функциональность будет приниматься так же,
как принимались M1–M8.

A. ЦИКЛ ВЕРИФИКАЦИИ ИНЕРТЕН

Все задачи канонического плана несут default из plan.py:

policy="self"
max_revision_attempts=0
deterministic_checks=[]

Из-за этого IMPLEMENTED достигает VERIFIED без запуска независимого
верификатора. В журнале прогона v0.9 восемь задач из девяти имеют событие
verification_passed с деталью "self", записанное в ту же секунду, что и
implementation_completed. Подсистема верификации существует и не работает.

B. TEST SUITE ЗЕЛЁНЫЙ ТОЛЬКО ВНУТРИ CODEX-СЕССИИ

260 тестов проходят при выставленном CODEX_THREAD_ID и дают 31 ошибку
и одно падение без него. Ни один тест переменную не выставляет,
а .github/workflows/tests.yml запускается в чистом окружении.
То есть заявленный CI не проходит и не проходил.

C. МЁРТВЫЙ КОД ОТ ВЫВЕДЕННОГО ТРАНСПОРТА

Примерно 1145 строк не вызываются из продакшена: подготовка Desktop-слотов,
плоскость авторизации транспорта, ветка auto-recovery в PipelineIncidentStore.
lifecycle.py при этом 4832 строки, из которых живой путь создания — около 1400.


==================================================
GOAL OF v1.0
==================================================

v0.9 обеспечил инвариант для результата работы:

IMPLEMENTED != VERIFIED

v1.0 распространяет этот инвариант на всё остальное доверенное состояние
и вводит профессиональную компетенцию как первоклассную сущность.

Итоговый инвариант продукта:

НИКАКОЕ ЗНАЧИМОЕ ИЗМЕНЕНИЕ ДОВЕРЕННОГО СОСТОЯНИЯ — ВКЛЮЧАЯ САМ ПЛАН —
НЕ ПРОДВИГАЕТСЯ ДАЛЬШЕ БЕЗ СООТВЕТСТВУЮЩЕГО УРОВНЯ ПРОВЕРКИ.

Целевой конвейер:

USER GOAL
  -> GOAL CONTRACT
  -> PLAN PROPOSED
  -> PLAN VERIFIED
  -> EXECUTION
  -> ARTIFACT PROPOSED
  -> ARTIFACT VERIFIED
  -> CANONICAL STATE

В v0.9 реализованы только последние три шага, и то частично.

==================================================
0. ПОЧИНИТЬ ПРИЁМКУ ДО ВСЕГО ОСТАЛЬНОГО
==================================================

Не начинай новую функциональность, пока не закрыты A, B и C выше.

Требуется:

- каждая задача канонического плана объявляет policy="independent",
  max_revision_attempts>=2 и хотя бы одну deterministic check,
  чья argv запускает полный сьют в чистом окружении;

- применение default policy="self" к канонической задаче отклоняется
  на валидации плана с явной ошибкой, а не принимается молча;

- тесты проходят без внешнего CODEX_THREAD_ID: тесты, которым нужна
  identity relay owner, передают её явно, а не читают из os.environ;

- заявленный CI зелёный;

- удалён мёртвый код: prepare_desktop_thread,
  retire_incompatible_legacy_desktop_session, production_send_payload,
  acknowledge_active_writer_release, acknowledge_desktop_launch,
  resume_desktop_run, descriptor_payload, pending_descriptors,
  reserve_authorized_transport_request, require_authorized_transport,
  bind_authorized_transport; в PipelineIncidentStore — claim_transport,
  mark_transport_requested, reconcile_transport, claim_auto_recovery,
  record_recovery_action, complete_auto_recovery,
  reconcile_recovery_after_crash, activate_pipeline_engineer,
  resolve_recovered, can_resume_task; RUNBOOKS, classify_incident,
  select_runbook, requires_pipeline_engineer, AuthorityProof,
  AuthorityKind, TransportClaim, TransportStatus; PlanChangeRequest,
  PlanChangeResult;

- lifecycle.py разрезан так, чтобы ни один модуль не превышал 1500 строк,
  и живой путь создания лежит в отдельном модуле;

- ensure_project_root больше не правит сохранённый проект молча:
  либо падает с точным указанием расхождения, либо записывает явное
  видимое пользователю решение.

ОТДЕЛЬНО — PREFLIGHT ДЛЯ ВСЕГО, ЧТО ТРЕБУЕТ TRUST

Первый production worker никогда не должен становиться BLOCKED только
потому, что Autopilot впервые пытается использовать собственный
built-in MCP или иную возможность, требующую доверия.

Неправильный UX:
  run -> M1 created -> worker starts -> first MCP call -> trust prompt -> BLOCKED

Правильный:
  preflight -> проверить доступность -> безопасный probe
  -> если нужен approval пользователя, запросить ДО создания первого воркера
  -> approve один раз -> preflight OK -> только тогда старт M1

Обход trust запрещён: никаких auto-approve, bypass, опасных флагов,
ручной правки trust DB и тихой эскалации прав. Запрос допустим,
но он происходит до запуска реального milestone, а не посреди него.

Живой путь reserve_ready_frontier -> create_desktop_thread_via_app_server
-> run_automatic_app_server_turn -> complete_desktop_worker по поведению
не меняется, его тесты проходят без правок.


==================================================
1. GOAL CONTRACT
==================================================

Runtime начинается не с DAG, а с контракта цели.

Goal Contract фиксирует не пересказ просьбы пользователя, а:

- required outcomes;
- обязательные deliverables;
- constraints;
- критерии конечного успеха (global acceptance).

Пример:

Vertical Slice Goal Contract

Required outcomes:
- player can enter playable level
- core movement works
- one combat encounter exists
- one weapon usable end-to-end
- representative environment exists
- UI supports required gameplay
- build can be packaged and launched

Global acceptance:
- no blocker bugs
- packaged build launches
- critical gameplay path completable

Контракт — структурированные поля, не проза.

Каждая задача графа объявляет, какой outcome контракта она производит.


==================================================
2. ВЕРИФИКАЦИЯ ПЛАНА
==================================================

Сейчас план — единственный артефакт без гейта. Runtime проверяет граф
на циклы, существование ссылок и resource constraints. Это линт:
он доказывает, что граф корректно сформирован, и ничего не говорит
о том, что он правильный.

Отказ тихий и дорогой: хорошо сформированный, но неверный план даёт
десятки честно VERIFIED задач, которые в сумме не составляют цель.
Все DoD выполнены, все верификаторы правы, результат не нужен.

Fresh plan verifier получает ТОЛЬКО:

- Goal Contract;
- constraints из Project Memory;
- предложенный DAG;
- DoD каждой задачи.

Он НЕ получает рассуждения планировщика.

Проверяет как минимум:

- Coverage — всё ли требуемое целью кто-то производит;
- Necessity — нет ли бессмысленной работы;
- Dependencies — имеют ли отношения смысл;
- DoD sufficiency — достаточно ли критериев, чтобы выполнение задачи
  означало что-то полезное;
- Integration completeness — есть ли точки, где несколько outputs
  должны быть собраны и проверены вместе.

Только PLAN_VERIFIED допускает scheduler к производству.
Граф, не прошедший верификацию, не может зарезервировать ни одной задачи.

Coverage проверяется детерминированно там, где возможно: outcomes контракта
перечислены, каждая задача объявляет свой output, покрытие считается кодом.


==================================================
3. ДРЕЙФ ПЛАНА И ПОЛНАЯ РЕВАЛИДАЦИЯ
==================================================

Replan-патчи проходят ту же верификацию, и строже.

Проверять каждый патч локально недостаточно: патчи накапливаются, и граф
уходит от исходной цели без единого момента, где кто-то смотрит на него
целиком. Корабль Тесея: каждый патч разумный, итоговый план решает
другую задачу.

После настроенного числа принятых патчей или при любом существенном
изменении critical path runtime выполняет:

FULL PLAN REVALIDATION

против исходного Goal Contract.

Существенные изменения critical path или самой цели могут требовать
approval человека.


==================================================
4. МЕХАНИЧЕСКАЯ И СЕМАНТИЧЕСКАЯ ПРИЁМКА
==================================================

Чем машинно-проверяемее контракт, тем точнее исполнитель оптимизируется
именно под него. Это прямое следствие требования писать DoD исполняемыми
проверками, и его надо зафиксировать явно.

Пример: asset opens, polycount within budget, UV present, materials
assigned, export succeeds, naming ok — всё это проходит на модели,
которая не является оружием.

Поэтому приёмка разделяется на два МЕХАНИЗМА, а не на два пункта списка:

Mechanical Acceptance
  Удовлетворяет ли артефакт измеримым ограничениям?

Semantic Acceptance
  Выполняет ли он заявленное назначение?

Задачи классифицируются:

- deterministic-complete — контракт полностью машинно проверяем
  (смена version field, преобразование схемы, конкретная миграция
  с исчерпывающим набором assertions). Автопроверка может дать VERIFIED,
  отдельный LLM-verifier только ухудшит экономику;

- mixed — зелёные проверки лишь ДОПУСКАЮТ результат к суждению,
  но сами по себе VERIFIED не дают;

- judgment — нужен независимый верификатор или человек.

Класс объявляется в плане и проверяется plan verifier на правдоподобность:
задача с субъективным результатом не может быть объявлена
deterministic-complete.


==================================================
5. ГЕЙТ НА ПОБОЧНЫЕ ЭФФЕКТЫ
==================================================

IMPLEMENTED != VERIFIED не значит ничего, если побочные эффекты наступили
на стадии IMPLEMENTED.

Воркер с write-инструментом уже сделал коммит, уже перезаписал ассет,
уже поменял файл к моменту, когда верификатор говорит REVISE.
Другие воркеры это уже читают.

Инвариант формулируется не как «воркер никогда не пишет», а:

НЕПРОВЕРЕННЫЙ OUTPUT НЕ ДОЛЖЕН БЕСКОНТРОЛЬНО СТАНОВИТЬСЯ
CANONICAL SHARED STATE.

Схема:

Worker
  -> proposed change / staged artifact
  -> Verification
  -> accepted
  -> runtime promotes change
  -> canonical project state

Для кода — patch, branch или isolated worktree.
Для файлов — staging directory.
Для сгенерированных ассетов — новая version до promotion.
Для систем, где надёжно разделить production и staging невозможно —
максимально узкий write scope, resource locks, snapshots/rollback
и при необходимости human approval; исключение объявляется явно
и записывается, а не подразумевается.

Побочный выигрыш: у верификатора появляется настоящий артефакт вместо
«сходи посмотри, что теперь в репозитории».


==================================================
6. WRITE SCOPE
==================================================

Каждый worker несёт явное поле Write Scope: какое состояние он имеет право
предлагать или изменять и по какому пути.

Запись вне объявленного scope падает закрыто.

Resource locks дополнительно покрывают артефакты, а не только инструменты:
две задачи, трогающие один файл Figma или один ассет, конфликтуют,
даже если держат разные локи на инструмент.


==================================================
7. SKILL PACKS
==================================================

Сегодня специалист — только RoleProfile, собранный планировщиком
и выброшенный после задачи. Название профессии не создаёт компетентность.

Skill pack — долговечная, версионированная, композируемая, независимо
тестируемая единица. Маленький модуль, никогда не personality prompt.

Объявляет:

- стабильный id и семантическую версию;
- какую capability даёт;
- процедуры, чеклисты, режимы отказа, критерии качества;
- требуемые инструменты и MCP-серверы;
- deterministic checks, квалифицирующие воркера на его использование;
- роли evidence, которые он имеет право записывать.

Композиция вместо монолита:

Role      3D Artist
Craft     Hard Surface Modeling
Tool      Blender
Pipeline  Unreal Asset Export
Quality   Realtime Asset Optimization
Project   проект пользователя Art Direction
Project   Weapon Technical Constraints

Autopilot перед задачей собирает нужный Skill Stack: для мелкой задачи
два-три модуля, для серьёзного production — шесть-восемь.

КРИТИЧЕСКОЕ РАЗДЕЛЕНИЕ:

Skill Requirements — чем профессия обязана владеть.
Loaded Skills — что реально грузится в контекст под конкретную задачу.

У Senior 3D Artist может быть двадцать компетенций в профиле,
но чтобы поправить pivot одного ассета, воркер получает две-три.
Это даёт одновременно высокий профессиональный стандарт
и маленький context footprint.

Skills НИКОГДА не выбирают модель. Capability routing остаётся
единственным селектором модели; pack может только объявить
требуемую capability.


==================================================
8. ЧЕТЫРЕ ИСТОЧНИКА НАВЫКОВ
==================================================

Если Studio будет каждый раз просить модель «придумай себе Skill
Senior 3D Artist», получится тот самый Вася, который сам написал себе
резюме и сам решил, что он senior.

1. Vetted Skill Library
   Базовые профессиональные навыки известного происхождения,
   поставляются со Studio или устанавливаются отдельно.
   Не персонажи, а проверенные procedures, checklists, tool usage,
   failure modes, quality criteria.

2. Project-generated Skills
   Специализированный профиль, собранный из базовых packs
   плюс Project Memory и файлы проекта.

3. Missing Skill Synthesis
   Если нужной компетенции нет вообще, модель может написать новую.
   Она получает статус CANDIDATE SKILL и не становится доверенной сразу.
   Проверяется через authoritative documentation, реальные tools,
   tests, verifier или первые рабочие результаты.

   Need capability: Houdini destruction pipeline
   No trusted skill found
   -> research authoritative docs
   -> generate candidate skill
   -> test procedure
   -> verify outputs
   -> promote to trusted skill

4. Learned Skills
   Обновление существующих packs по подтверждённому evidence
   согласно правилам раздела 16.

Самогенерация — fallback и learning mechanism, а не единственный
источник компетенции.


==================================================
9. ROLE SPECIFICATION — НАЙМ ПРОФЕССИИ
==================================================

Когда проекту впервые нужен новый тип роли, Studio создаёт не воркера,
а профиль профессии.

Need: Senior 3D Artist
-> определить, что этот специалист должен уметь именно в этом проекте
-> найти существующие релевантные skills
-> проверить их качество и происхождение
-> выбрать только нужные
-> собрать competency profile
-> только после этого создать worker

Отбор, а не «найди все skills про 3D и установи» — иначе получится
помойка из перекрывающихся инструкций, конфликтующих правил, огромного
контекста и потенциально небезопасных сторонних skills.

Критерии отбора:

- что требуется текущему проекту;
- насколько skill авторитетный;
- когда обновлялся;
- что именно добавляет;
- не дублирует ли установленное;
- не конфликтует ли с другими;
- требует ли executable code / shell / внешнего доступа;
- подтверждал ли качество на прошлых задачах.

Профиль версионируется: Senior 3D Artist v1.4.

Первый найм профессии дорогой, потому что организация определяет
требования, процессы и стандарты. Последующие воркеры этой профессии
получают готовый onboarding, и вопрос сужается до:
нужны ли для ЭТОЙ задачи дополнительные skills.


==================================================
10. ОРГАНИЗАЦИЯ ВЫВОДИТСЯ ИЗ ПРОЕКТА
==================================================

Ни роли, ни отделы не зашиты под конкретную индустрию.

PROJECT GOAL
  -> понимание проекта
  -> требуемые артефакты
  -> требуемые capabilities
  -> динамические роли
  -> skill packs для каждой роли
  -> ограничения и память проекта
  -> workers

Для геймдева получится Game Design / Art & 3D / Gameplay / UI / QA.
Для SaaS — Product / Frontend / Backend / Data / Security.
Для исследования — Research / Analysis / Fact Checking / Editing.
Для рекламной кампании — Strategy / Creative / Production / Distribution.
Для маленького проекта отделов может не быть вообще.

Даже одинаковая роль специализируется под проект:
UI Designer · B2B Analytics и UI Designer · Mobile Casual Game —
разный skill и context mix.

Пользователь не выбирает шаблон «Game Studio». Организационная структура
является результатом планирования проекта и меняется вместе с ним.


==================================================
11. CAPABILITY BROKER
==================================================

MCP почти никогда не даёт нужной гранулярности: токен GitHub
репозиторный, доступ Figma файловый или командный. «Junior UI Designer
получает только Figma» на практике означает доступ ко всему файлу.

Между worker и внешними tools стоит Capability Broker.

Он отвечает не на вопрос:
  есть ли у worker доступ к GitHub?

а на вопрос:
  какие операции, над каким repo, branch, artifact или resource
  разрешены ЭТОЙ конкретной задаче?

Read capabilities выдаются относительно свободно.
Write capabilities требуют существенно более строгого контроля
и подчиняются разделам 5 и 6.

Least privilege — отдельная инфраструктура, а не то, что даёт MCP сам.


==================================================
12. ГРАНИЦА ДОВЕРИЯ ДЛЯ ВНЕШНЕГО ВВОДА
==================================================

Всё, что приходит из внешнего MCP — комментарии Figma, тексты issues
и PR, страницы документации, заметки в аналитике, внутренние вики —
написано людьми и всё чаще другими агентами. Это недоверенный ввод.

У обучающейся системы есть путь, которого нет у обычного чат-агента:

внешний текст
  -> worker поверил
  -> Project Memory truth
  -> Learning Candidate
  -> trusted Skill
  -> применяется ко ВСЕМ будущим workers профессии

То есть комментарий в issue при неудачном стечении обстоятельств
становится производственным стандартом организации.

Каждый evidence object хранит provenance и уровень доверия:

human + verification  >  deterministic tool output  >  external text

Промоушен в Project Memory truth — только с определённого уровня.
Промоушен в Skill — с ещё более высокого, плюс доказательство
улучшения исхода.


==================================================
13. PROJECT MEMORY — ОДНО ХРАНИЛИЩЕ
==================================================

Art Direction, Game Design, Architecture, Product, Brand, Security —
это типизированные SCOPES единой Project Memory, а не отдельные
MCP-серверы и не отдельные источники истины.

Пять мест, где живёт правда, дают дублирование, расхождение evidence
и отсутствие единой процедуры разрешения конфликтов. Инвариант
No Evidence -> No Truth держится ровно на том, что хранилище одно.

MCP остаётся тем, чем является: протоколом к системам, которыми
Autopilot не владеет. Project Memory может быть доступна workers
через MCP-интерфейс технически, но концептуально остаётся единственным
внутренним state store.


==================================================
14. СРОК ЖИЗНИ ПРАВИЛ
==================================================

Project Memory не является вечным архивом immutable truth.

У «руководства как данных» есть издержка: правила стареют, и, в отличие
от живого лида, хранилище этого не замечает.

Constraints и decisions имеют version, provenance и возможность
invalidation.

Готовый сигнал: когда верификаторы систематически отклоняют работу,
которая формально удовлетворяет заявленному правилу — сломано правило,
а не работа.

Всплеск таких отклонений в одном scope — триггер на rule review
или replanning. Это же связывает Project Memory, verification
и planning в один feedback loop.


==================================================
15. WARM WORKER REUSE
==================================================

Fresh workers остаются базовым механизмом. Чистый контекст —
защита от накопленной истории и устаревших предпосылок.

Ценность тёплого воркера НЕ в повторяющемся контекстном префиксе —
его закрывает prompt caching. Она в состоянии окружения: загруженная
сцена Blender, поднятый dev server, авторизованная сессия в инструменте,
прогретые индексы, уже проделанная разведка по коду.

Поэтому критерий reuse — не семантическая близость задач,
а стоимость восстановления ОКРУЖЕНИЯ.

Lifecycle:

NEW -> WORKING -> WARM_IDLE -> (REUSED | RETIRED)

WARM_IDLE не потребляет ничего.

v1 reuse — булево правило, не score:

- тот же проект;
- та же роль;
- тот же resource set;
- короткий TTL;
- никаких изменений этих ресурсов с последней работы воркера.

Всё остальное создаёт fresh worker.

Переиспользованный воркер получает явный delta sync того, что изменилось
с его last_seen. Delta, которую нельзя вычислить полностью, форсирует
fresh worker.

Отказ тёплого воркера тихий и мерзкий: он действует из устаревшей
посылки, которой нет в delta, выдаёт правдоподобный результат,
а верификатор не видит транскрипт и поймать это не может. Поэтому
его output несёт маркер в evidence — чтобы отказы по устаревшей
посылке были атрибутируемы.

Reuse выключен по умолчанию и документируется как оптимизация.

Телеметрия пишет по каждому решению оценочную и фактическую экономию
против fresh bootstrap.

Никакой reuse score, модель семантической локальности или эвристика
freshness не реализуются, пока телеметрия не покажет существенную
экономию от булева правила.


==================================================
16. LEARNING LOOP
==================================================

Autopilot не меняет веса моделей. Он улучшает собственную
production system.

Повторяющееся наблюдение верификатора САМО ПО СЕБЕ недостаточно
для изменения Skill. Иначе в skills кодируются предпочтения
верификатора и становятся производственным стандартом — замкнутый
контур без ground truth. Обновление role skill попадает во всех будущих
работников профессии, то есть это усилитель систематической ошибки.

Цепочка:

Observation
  -> Learning Candidate
  -> доказательство улучшения ИСХОДА
  -> promotion

Доказательством является: снижение числа ревизий, рост first-pass
acceptance, снижение человеческих переделок, улучшение детерминированных
метрик качества. Не «verifier трижды это отметил».

Три уровня с разным порогом:

Project lesson
  Меняет только конкретный проект. Принимается относительно легко.

Role Skill
  Влияет на всех будущих специалистов профессии.
  Требует существенно более сильного evidence.

Global production policy
  Влияет на всю систему. Порог высокий,
  может требовать approval пользователя.

ВАЖНОЕ СЛЕДСТВИЕ ПО МАСШТАБУ:

чтобы показать, что правка Role Skill подняла first-pass acceptance,
нужна выборка задач этой роли. В одном проекте их будет пятнадцать —
эффект такого размера не детектируется ничем.

Значит обучение на уровне профессий либо не срабатывает никогда,
либо требует агрегации по многим проектам. Реализуй локальную запись
и агрегацию так, чтобы флитовая агрегация была возможна позже,
но по умолчанию данные оставались проектными, с явной opt-in границей
и заявленным механизмом изоляции между тенантами — механизмом,
а не декларацией.


==================================================
17. КОНТЕКСТ КАК РЕСУРС
==================================================

Каждый worker не получает всю историю проекта.

Context Broker формирует минимальный стартовый пакет, дальше —
progressive disclosure:

small bootstrap
  -> work
  -> нужно ещё?
  -> selective retrieval релевантного evidence
  -> continue

Задача объявляет context_scope и context_budget наряду с model,
reasoning, role и skills.

Микрозадачи с высокой локальностью бандлятся: если несколько задач
делят роль, файлы, skill и состояние зависимостей, создаётся один
fresh worker на связанную группу — чтобы стоимость bootstrap
не превышала стоимость самой работы. Это не возврат к бесконечному
чату, а амортизация bootstrap cost.

Логика:

micro + тот же домен/ресурс      -> объединять
независимые обычные задачи        -> отдельные fresh workers
большая задача                    -> отдельный worker с большим бюджетом
investigation                     -> маленький старт + расширение по требованию


==================================================
18. БЮДЖЕТ КАК РАСПРЕДЕЛЯЕМЫЙ РЕСУРС
==================================================

Budget сейчас задуман как поле воркера, константа на задачу.

Но scheduler знает critical path. Задача на критическом пути заслуживает
трёх попыток и дорогой модели; лист — одной и дешёвой.

Иначе attempt 3/3 на графе из двухсот задач — это способ сжечь allowance
равномерно вместо того, чтобы вложить его туда, где он решает.

Budget распределяется планировщиком по структуре графа и включает
токены, время, число попыток и уровень reasoning.


==================================================
19. СЕМАНТИЧЕСКИЕ КОНФЛИКТЫ
==================================================

Resource locks защищают файлы, приложения, базы и немерджабельные ассеты.
Этого недостаточно.

Две параллельные задачи могут писать РАЗНЫЕ файлы и при этом принять
несовместимые архитектурные решения об одной и той же системе.

Project Memory поддерживает decision ownership / decision locks
для критических открытых вопросов.

Точки схождения нескольких независимых ветвей получают integration
или consistency verification.

Параллельность не является самоцелью: если граф почти последовательный,
пять воркеров ради ощущения AI-команды не создаются.


==================================================
20. REVISE И СТАБИЛЬНОСТЬ РУБРИКИ
==================================================

Два разных fresh-верификатора имеют разную строгость. Задача может пройти
с третьей попытки не потому, что стала лучше, а потому что попался мягкий
проверяющий. Это недетерминизм под видом контроля качества.

Требуется:

- attempt budget на каждую задачу, эскалация человеку при исчерпании;
- стабильная рубрика верификатора между попытками, хранимая
  в Project Memory;
- логирование verifier disagreement rate;
- обратная связь верификатора переезжает в следующую попытку
  как evidence.

Fresh implementer не получает весь старый транскрипт, но получает
конкретно подтверждённые причины предыдущего rejection:

fresh context + verified revision evidence

Чистый контекст не означает потерю урока.


==================================================
21. DEVOPS: RECOVERY LANE В ДВА УРОВНЯ
==================================================

Не постоянный DevOps-агент, сидящий в чате вечно, а постоянная
DevOps-ФУНКЦИЯ, под которую агент поднимается только когда runtime
видит инфраструктурный сбой.

Текущий failure mode:

  что-то сломалось -> BLOCKED -> ждём человека

Целевой:

  что-то сломалось -> self-recovery -> продолжили

Recovery lane:

WORKER FAILED
  -> определить: ошибка задачи или ошибка пайплайна?
  -> если pipeline / runtime / integration / tooling
  -> DEVOPS / PIPELINE ENGINEER
  -> диагностирует
  -> чинит или предлагает remediation
  -> повторный health check
  -> resume affected tasks

УРОВЕНЬ 1 — ДЕТЕРМИНИРОВАННОЕ SELF-HEALING

Runtime сам, без модели, умеет:

- перезапустить App Server;
- переподключить MCP;
- очистить stale cache;
- пересоздать slot;
- unsubscribe / resubscribe;
- проверить cwd и project assignment;
- восстановить worker после crash;
- повторить безопасный tool call;
- проверить locks;
- выполнить healthcheck.

Только если это не помогло — уровень 2.

УРОВЕНЬ 2 — FRESH PIPELINE ENGINEER

Получает не весь проект, а incident package:

INCIDENT
M1 blocked

ERROR
already has an active writer

SYSTEM STATE
Desktop connected
App Server healthy
project assignment valid
worker cwd valid

RECENT EVENTS
...

ALLOWED ACTIONS
restart slot
unsubscribe thread
clear plugin cache
reconnect MCP

DO NOT
change global Codex settings
delete project state
modify unrelated files

Lifecycle:

HEALTHY -> DEGRADED -> AUTO_RECOVERY -> RECOVERED
                                     -> AUTO_RECOVERY_FAILED
                                        -> PIPELINE_ENGINEER -> RESOLVED
                                                             -> ESCALATE_TO_USER

ГРАНИЦА, КОТОРУЮ НЕЛЬЗЯ ПУТАТЬ

Pipeline Engineer обязан отличать ошибку production work
от ошибки инфраструктуры:

3D Artist не может сделать модель        -> НЕ DevOps, это production
Blender MCP не отвечает                  -> DevOps
Git worktree конфликтует                 -> DevOps
worker не попал в нужный Codex Project   -> DevOps
verifier считает результат плохим        -> НЕ DevOps, это revision

Человек нужен только если: требуется опасное permission; нужно менять
глобальную конфигурацию; починка может повредить проект; recovery
несколько раз не сработал; нужен продуктовый или архитектурный выбор.

ПРОМПТ РОЛИ

Пишется с дисциплиной промпта независимого верификатора: свежий контекст,
никакой самооценки исполнителя, никакой истории транскрипта, ограниченный
incident package, одна структурированная протокольная строка на выходе.

- промпт несёт класс инцидента, фазу, затронутые task id, ограниченное
  состояние системы и недавние события — и ничего больше; он никогда
  не получает содержание production-задачи или утверждения другого воркера;

- промпт перечисляет allowlisted действия выбранного runbook и явно
  указывает, что production quality failures, approvals, обход trust,
  глобальные настройки, удаление состояния и создание задач вне области;

- ЛЮБОЕ утверждение о внешнем ограничении, ограничении платформы,
  невозможности API или поведении «by design» недействительно,
  если в ответе нет точной команды и её дословного вывода.
  Слова «подтверждено», «не позволяет», «единственное ограничение»
  без воспроизведения — это неполный результат, а не находка;

- путь автоматического восстановления подключён к продакшену:
  claim_auto_recovery ... complete_auto_recovery
  и reconcile_recovery_after_crash достижимы из живого диспетчера,
  с тестами на ограниченный retry, гейт healthcheck и эскалацию
  пользователю при AUTO_RECOVERY_FAILED;

- последняя непустая строка — ровно один структурированный JSON-результат
  с вердиктом resolved или escalate, id runbook и исходом healthcheck.

В статусе роль отображается как состояние, а не как сотрудник:
"Pipeline Engineer · On call · healthy" или
"Pipeline Engineer · Incident #18 · recovering MCP".

==================================================
22. МЕТРИКИ
==================================================

«Agents running» — плохая метрика.
Количество VERIFIED задач недостаточно: система способна безупречно
выполнить ненужную работу.

Главный ground truth на раннем этапе:

HUMAN REWORK AFTER VERIFIED

Как часто пользователь вынужден переделывать то, что Autopilot уже
счёл принятым. Держать в паре с долей отказов на стадии интеграции —
там оседает отложенный брак, который не виден при первом взгляде.

Дополнительно:

- deterministic DoD coverage;
- first-pass verification rate;
- verifier disagreement rate;
- число ревизий;
- вмешательства человека;
- usage на принятый артефакт;
- wall-clock;
- задержка критического пути.

Доля задач с детерминированным DoD — внутренняя метрика здоровья
системы, а не отчётность.


==================================================
23. ЭКСПЕРИМЕНТ
==================================================

Главный тезис продукта ни разу не измерен.

Реализуй режим прогона, позволяющий сравнить четыре арии на одном
наборе задач:

арии 1  baseline autonomous execution
арии 2  + явный письменный DoD, без проверок
арии 3  + детерминированные проверки
арии 4  + независимый верификатор

Требования:

- стоимость, wall-clock и Human Rework After VERIFIED пишутся по каждой
  арии; переделки оценивает человек, НЕ знающий, какая ария выдала
  результат;

- отчёт прямо указывает, концентрируется ли выигрыш в арии с явным DoD —
  в этом случае продукт является компилятором спецификаций,
  а не evidence-gated runtime, и позиционирование должно измениться;

- если разница в пределах шума, отчёт говорит это без смягчения.

Домен для доказательства — код, а не креативное производство:
там доля машинно-проверяемого DoD максимальна, и переделки наблюдаемы
объективно прямо из git, без опроса людей.


==================================================
24. ПОЗИЦИОНИРОВАНИЕ И ДОКУМЕНТАЦИЯ
==================================================

Продукт не позиционируется как «наймите своих AI-сотрудников»
и не прежде всего как «постройте свою AI-компанию». Орг-метафора
роднит его ровно с тем классом продуктов, от которого он отстраивается.

Точная формулировка:

Autopilot — production runtime для длинных AI-проектов, в котором
LLM планирует и выполняет интеллектуальную работу, но ни результат,
ни знание, ни изменение общего состояния не получают доверия
автоматически. Работа движется дальше только вместе с достаточным
evidence.

Dynamic roles, Skill Stacks, fresh workers, warm reuse, MCP и semantic UI
являются механизмами достижения этого свойства, а не самим свойством.

Два уровня продукта:

Codex Autopilot OSS — локальный execution runtime: planning, DAG,
Project Memory, evidence, workers, routing, verification, resource
management, recovery и базовый Skills layer. Должен оставаться реально
полезным продуктом.

Autopilot Studio — коммерческий production environment поверх runtime:
visual workspace, dynamic organization, skill management, evidence
inspection, policies, permissions, Capability Broker, organizational
learning, usage intelligence, collaboration, integrations.

Studio продаёт не искусственно отрезанную функциональность, а масштаб,
observability, control и organizational intelligence.

Документация обновляется по факту кода, а не по намерению.


==================================================
25. БЕЗОПАСНОСТЬ
==================================================

Не вводится:

- обход safety;
- автоматическое подтверждение approvals;
- неограниченный filesystem/shell MCP;
- тихая эскалация прав;
- автоматический push/tag/release;
- принудительная очистка Git.

Worker не отвечает на approvals. Никакой компонент не говорит от имени
пользователя. Capability Broker сужает права, а не расширяет.


==================================================
ТЕСТЫ
==================================================

T1  Goal Contract со структурированными outcomes загружается
    и валидируется; задача, не объявившая производимый outcome,
    отклоняется.

T2  Хорошо сформированный, но неполный план не проходит plan verification
    по coverage и не может зарезервировать ни одной задачи.

T3  План с лишней работой отклоняется по necessity.

T4  Последовательность принятых патчей, уводящая граф от контракта,
    ловится FULL PLAN REVALIDATION.

T5  Plan verifier не получает рассуждения планировщика; тест проверяет
    состав промпта, а не только результат.

T6  Задача класса judgment, объявленная deterministic-complete,
    отклоняется на валидации плана.

T7  Воркер производит staged artifact; canonical state не меняется
    до VERIFIED; REVISE не оставляет следов в canonical state.

T8  Запись вне объявленного Write Scope падает закрыто.

T9  Две задачи, трогающие один артефакт через разные инструменты,
    конфликтуют.

T10 Skill pack резолвится по id и версии; CANDIDATE, указанный
    как trusted, отклоняется.

T11 Skill Requirements и Loaded Skills различаются: роль с двадцатью
    компетенциями грузит только нужные задаче, собранный промпт
    укладывается в context budget.

T12 Конфликтующие или дублирующие packs детектируются на резолве
    и падают закрыто, а не конкатенируются в промпт.

T13 Skill pack не может выбрать модель; попытка объявить модель
    отклоняется.

T14 Роль, не прошедшая eval для capability, не может быть назначена
    на требующую её задачу; отказ называет недостающий eval.

T15 Performance record пишется только из авторитетных исходов
    верификации; самооценка исполнителя не может попасть в запись.

T16 Агрегат возвращает ранжированные сочетания role/model/tool
    с размером выборки и отказывается ранжировать ниже документированного
    минимума.

T17 Capability Broker сужает права до задачи; запрос операции вне выданной
    capability отклоняется до обращения к внешнему серверу.

T18 Внешний текст из MCP не может быть промоутнут в Truth без требуемого
    уровня provenance; цепочка external text -> Skill невозможна
    без прохождения порогов.

T19 Scope Project Memory не является отдельным хранилищем: конфликт
    в одном scope разрешается общей процедурой.

T20 Правило, которому работа формально удовлетворяет, но которая
    систематически отклоняется, поднимает rule review.

T21 Warm reuse срабатывает только при выполнении всех условий булева
    правила; изменение ресурса с последней работы форсирует fresh worker.

T22 Delta sync, который нельзя вычислить полностью, форсирует fresh worker.

T23 Learning Candidate не промоутится без доказательства улучшения исхода;
    промоушен Role Skill требует большего порога, чем project lesson.

T24 Budget распределяется по критическому пути: задача на нём получает
    больше попыток, чем лист.

T25 Микрозадачи с общей локальностью бандлятся в одного воркера;
    независимые — нет.

T26 Decision lock не даёт двум параллельным задачам принять несовместимые
    решения по одному открытому вопросу.

T27 Рубрика верификатора стабильна между попытками; verifier disagreement
    rate записывается.

T28 Обратная связь верификатора доезжает до следующей попытки как evidence
    при чистом контексте исполнителя.

T29 Pipeline Engineer: утверждение о внешнем ограничении без команды
    и её вывода классифицируется как неполный результат.

T30 Все тесты проходят в чистом окружении без CODEX_THREAD_ID.


==================================================
CRITICAL ACCEPTANCE CRITERIA
==================================================

A. GOAL CONTRACT
   Цель выражена структурированным контрактом, а не прозой.

B. PLAN VERIFICATION
   План проходит тот же propose -> verify -> accept, что и работа.

C. PLAN DRIFT
   Накопление патчей ловится полной ревалидацией против контракта.

D. SIDE-EFFECT GATE
   Непроверенный output не становится canonical shared state.

E. WRITE SCOPE
   Каждый воркер объявляет, что имеет право менять; выход за scope
   падает закрыто.

F. SKILL COMPOSITION
   Компетенция — стек маленьких версионированных модулей,
   а не personality prompt.

G. SKILL PROVENANCE
   Самосгенерированный навык не становится доверенным немедленно.

H. PROFESSION HIRING
   Первый найм профессии создаёт версионированный профиль,
   последующие его переиспользуют.

I. QUALIFICATION
   Роль без пройденного eval не допускается к классу работ.

J. PERFORMANCE RECORD
   История качества пишется только из авторитетных исходов.

K. LEAST PRIVILEGE
   Capability Broker сужает права до конкретной задачи.

L. TRUST BOUNDARY
   Внешний текст не становится производственным стандартом
   без прохождения порогов.

M. SINGLE MEMORY
   Один state store с типизированными scopes, не пять источников истины.

N. RULE LIFETIME
   Устаревшее правило обнаруживается по расхождению «формально
   соответствует / систематически отклоняется».

O. WARM REUSE IS OPTIONAL
   Выключен по умолчанию, булево правило, измеряемая экономия.

P. LEARNING REQUIRES OUTCOME
   Промоушен навыка требует доказательства улучшения исхода.

Q. BUDGET ALLOCATION
   Бюджет распределяется по структуре графа.

R. SEMANTIC CONFLICTS
   Параллельные задачи не принимают несовместимые решения.

S. VERIFICATION IS ON
   Ни одна каноническая задача не принимается policy="self".

T. GREEN CI
   Заявленный CI проходит в чистом окружении.

U. NO CONTROLLER LLM
   Scheduler остаётся детерминированным кодом.

V. SERIAL COMPATIBILITY
   Существующие проекты v0.9 остаются валидными.

W. SECURITY
   Никакого обхода прав, автоапрувов и автопубликации.

X. SIMPLE UX
   Обычному пользователю по-прежнему достаточно дать цель проекта.
